# Pi Issues Selector

1. Read [`../../README.md`](../../README.md) for the reference syntax, how the Issue Repository is chosen, and the popup's requirements. `#` is an issue (a pull request too on GitHub); `!` is a GitLab merge request.
2. For missing suggestions, confirm extension loading and interactive mode, then type `#` after a space in ordinary prose (a lone `#` at the start of a line is a Markdown heading marker; the popup opens after the next character). Check `git config --get-regexp '^remote\..*\.(url|gh-resolved|glab-resolved-base|glab-resolved)$'` in the session directory for the Issue Repository, and `gh auth status` (GitHub) or `glab auth status --hostname <host>` (GitLab) for the repository's host. Run `gh api --hostname <host> 'repos/<owner>/<repo>/issues?state=all&sort=updated&per_page=100'` (GitHub), or `glab api --hostname <host> 'projects/<url-encoded owner/repo>/issues?state=all&order_by=updated_at&sort=desc&per_page=100'` (GitLab, with `merge_requests` for the `!` popup; encode the whole `group/sub/project` path, `/` as `%2F`) to see the listing the popup reads. A GitLab `404` is the sign-in notice too: `glab api` sends unauthenticated requests when signed out, so a private project answers 404, and a project that disables issues or merge requests answers 404 as well. A message that starts with `!` is a bash command in Pi, so no `!` popup opens there. Finish when the popup lists the expected items or a named boundary (no remote whose host name an Issue Host serves, `gh` or `glab` missing or signed out, private repository, a project that disables issues or merge requests, rate limit, network) explains their absence.
3. For a missing or wrong link, compare the typed reference with the submitted user message and the Issue Repository's remote. Check the literal contexts (escaped, in code, inside a link, `issue#123`, `#123abc`) and whether an Issue Host serves the selected remote's host name: `github.com`, `ssh.github.com`, `*.ghe.com`, `gitlab.com`, a host `gh` lists, or a host `glab` lists (an SSH host alias stays literal). For GitLab, check the remote's path has 2 to 21 valid segments and the reference's qualifier too (`group/sub/proj#12`; `proj#12` is not supported). Finish when the link targets that repository or a named boundary explains the mismatch.
4. For "my GitHub Enterprise Server host isn't recognised": confirm the selected remote's host with the `git config` command above (selection never falls through to another remote), then check that its lower-cased name is a top-level key of `gh`'s `hosts.yml` (key names only; never print or paste values, the file may hold tokens) or equals a non-empty `GH_HOST`. The file is `$GH_CONFIG_DIR/hosts.yml`, else `$XDG_CONFIG_HOME/gh/hosts.yml`, else on Windows `%APPDATA%\GitHub CLI\hosts.yml`, else `~/.config/gh/hosts.yml`; empty variables count as unset, and a missing or malformed file recognises nothing without an error. Fix with `gh auth login --hostname <host>`; it takes effect on the next message. Also check for an SSH host that differs from the web host or an SSH alias (both stay literal unless `gh` lists that name), and for a host also configured for another service (unrecognised). Finish when the host is recognised or one of these boundaries explains why not.
5. For "my self-managed GitLab host isn't recognised": confirm the selected remote's host with the `git config` command above (selection never falls through to another remote), then check that its lower-cased name is a key under `hosts:` in `glab`'s `config.yml`, or equals some `hosts.<h>.ssh_host` (then links use `<h>`). Read key names only; never print or paste values, the file holds plaintext tokens. The file is `$GLAB_CONFIG_DIR/config.yml` when that variable is non-empty (and nowhere else), else the first existing of `~/.config/glab-cli/config.yml` and `<base>/glab-cli/config.yml`, where `<base>` is a non-empty `$XDG_CONFIG_HOME`, else `~/Library/Application Support` (macOS), `%LOCALAPPDATA%` (Windows), or `~/.config`. Not counted: `glab`'s top-level `host`, `GITLAB_HOST`, `GITLAB_URI`, `GL_HOST`, the per-repository `<git-dir>/glab-cli/config.yml`. Fix with `glab auth login --hostname <host>`; it takes effect on the next message. A host listed by both `gh` and `glab` is unrecognised. An instance under a path prefix (`https://host/gitlab/…`) links correctly but has no popup. Finish when the host is recognised or one of these boundaries explains why not.
6. If the link is correct but the page is not what you expected, report conversion as working. On GitHub the link always uses `/issues/<number>`, which redirects to `/pull/<number>` for pull requests. On GitLab `#` links `/-/issues/<n>` and `!` links `/-/merge_requests/<n>`, which are separate numbers with no redirect between them: a merge request typed as `#` is the wrong link; use `!`. Keep this extension configuration-free.
