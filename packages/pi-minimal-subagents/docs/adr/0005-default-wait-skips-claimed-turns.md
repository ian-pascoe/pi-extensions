# Skip claimed turns in default `subagent_wait` selection

Without `turn_id`, `subagent_wait` selects the oldest observable turn whose result the parent has neither claimed nor been handed, in Delivery Ledger sequence order, and falls back to the active turn, then the latest turn, when none remains. This supersedes the default-selection rule of [ADR-0001](0001-wait-event-delivery-ordering.md), which prioritized the oldest claimed turn. That rule made the documented workflow (claim a result, `agent_message` the idle child, wait on the `started-turn`) return the already-claimed first result again, both while the new turn ran and after it was cancelled.

ADR-0001 otherwise remains in force. An explicit `turn_id` addresses any turn whose result is still retained, claimed or not, and returns the same settled result on repeated waits. A claimed wait-only terminal result stays retained, bounded at 20 per source per [ADR-0003](0003-persisted-delivery-ledger.md), until Delivery Evidence settles it; the wait's own tool result is that evidence, so once the wait is recorded and a newer turn has settled, an explicit wait on the older turn fails as no longer retained. A result counts as handed once automatic fallback has queued it to the parent, even before Delivery Evidence is reconciled. The marker is process-local: a reload either settles the result by its evidence or hands it over again, and a root turn boundary that shows Pi discarded the queued message releases it. A result that has not yet been handed, such as one still inside the wait-claim grace period or whose delivery failed, stays selectable, and waiting for it claims it. A default wait never repeats a result that automatic fallback already delivered. When the turn it selects, usually through the latest-turn fallback, was already handed by automatic fallback or has automatic Delivery Evidence on the caller's branch, the wait returns `event: "turn"` with `already_delivered: true`, the turn identity and status, and no output. It neither claims the turn nor counts as Delivery Evidence, so a discarded steer is still recovered as described below; it still drains Coordination Messages from that turn that were never handed. An explicit `turn_id` is unaffected and returns the full result. Claims remain durable Delivery Ledger state and behave as before across reloads and forks; automatic fallback is unchanged except for the discard recovery below. Settled turns the parent has neither claimed nor received are still returned oldest first.

## Consequences

ADR-0003 said a newer turn cannot strand an older claimed turn. That no longer holds for default waits. A turn claimed without Delivery Evidence, for example after a crash between the claim and the append of the wait's tool result, is never delivered automatically, and once a newer turn exists only an explicit `turn_id` reaches it. We accept this: the old rule broke the ordinary message-then-wait workflow on every use, while the stranded case needs a crash in a narrow window and stays recoverable by `turn_id`.

Pi's Esc (`clearQueue`) can discard a result already queued to the root as a steer, and Pi gives extensions no event for it. Pi does expose the messages it still holds at each `turn_end` boundary, and it persists a consumed steer before that boundary. So when a root `turn_end` reports no pending messages, a result handed while the root was running, before that turn's last message ended, either has Delivery Evidence on the root branch and settles, or was discarded. A discarded result loses its handed marker at once, so a default wait selects it again even when a newer turn exists, together with the Coordination Messages batched into it. If the root run goes on, as after a queue clear without an abort (dequeue or RPC `clear_queue`), automatic fallback steers the result back at once and the same run takes it. Esc aborts the run, and recovery never starts a root turn by itself, so the result waits: when the root's next run starts, whether from the user or from another delivery, unclaimed discarded results are steered into it in Delivery Ledger sequence, ahead of newer results still in their wait-claim grace period, so recipient-queue order is preserved. A branch change discards the pending re-send with the rest of the process-local state, and replay of the selected branch decides delivery. A result Pi still holds, including after an abort that did not clear the queue, keeps its marker, so nothing is delivered twice. When Esc lands outside a model turn, such as during a retry delay or compaction after the turn's last message, no boundary reports the empty queue until the root's next turn ends. Until then only an explicit `turn_id` or a reload reaches the result, and that boundary steers it into the still-running run. Until that boundary, a default wait reports the discarded result as `already_delivered`; an explicit `turn_id` returns it.
