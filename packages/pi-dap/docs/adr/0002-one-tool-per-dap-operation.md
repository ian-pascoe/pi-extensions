# One Pi tool per DAP operation

Each DAP operation is its own Pi tool, named `dap_<operation>` and grouped under the `dap` namespace. This replaces the single `dap` tool, which had one operation-discriminated schema. Every tool still acts on the one model-facing Debug Session from ADR-0001. Splitting the tools does not add sessions. Per-operation tools give each call a schema that holds only its own fields, and give permission extensions exact annotations: for example, `dap_stack` is read-only, but `dap_evaluate` can run arbitrary code. The `dap` tool is removed without an alias, in a breaking minor release.

Debugging is interactive, so every operation is `direct`: launch, set_breakpoints, continue, next, step_in, step_out, pause, stack, variables, evaluate, status, and stop. Declaring `dap_pause` costs one short description, and it is the only way to interrupt a Debuggee whose execution wait timed out, so it stays in view. The namespace remains: codemode's `describeNamespace("dap")` returns the group, and a future non-direct tool would join it.

Annotations follow what a call can do to the Debuggee and beyond. `dap_stack`, `dap_variables`, and `dap_status` are read-only and closed world; draining unread Debuggee output is Pi DAP bookkeeping, not a change to the Debuggee. Anything that runs the program's code is destructive and open world, because that code has the side effects the program has. That covers `dap_launch`, `dap_continue`, `dap_next`, `dap_step_in`, `dap_step_out`, and `dap_evaluate`, all non-idempotent. It also covers `dap_set_breakpoints`: a breakpoint `condition` passes through to the adapter and runs as Debuggee code at every hit. Replacing a file's Desired Breakpoints with the same list changes nothing further, so it is idempotent. `dap_pause` only interrupts, so it is idempotent and neither destructive nor open world. `dap_stop` is destructive and idempotent.

Each tool declares an `outputSchema` and returns `structuredContent` with complete data: state, all drained Debuggee output, Desired Breakpoints, and every row of the operation's result, shaped per operation so a result cannot carry a field its tool's schema omits. One deliberate exception: `dap_variables` with `frame_id` lists scopes the adapter marks expensive (such as js-debug's Global, thousands of rows) without expanding them, and a script or the model expands one with its `variables_reference`. Version 0.3.6 removed an output schema because it described only the bounded Observer UI details, which would have replaced complete results in codemode scripts; the details stay bounded and separate. A Debug Session state failure returns `isError` with the current state and an `error` field instead of throwing, so scripts can read it. Each description that can cause such a failure says so in one clause, and the `error` field's description renders in the tool's codemode declaration.

All tools are `executionMode: "sequential"` because they share the Debug Session. Pi runs a batch containing one sequentially, and in 1.0.0 it also queues nested calls that a codemode script starts together, for example with `Promise.all`, so calls never overlap on the Debug Session. The session needs no lock of its own. A script that starts `dap_continue` therefore cannot interrupt its wait with `dap_pause` in the same `Promise.all`; the pause queues behind the wait.

Namespace `instructions` exist only in Pi 1.0.0's `ToolNamespace`. There, codemode's `describeNamespace()` returns them and `tool_search` includes them in its ranking text. They are not part of tool listings, and Pi 0.99.0 has no such field. Each description therefore states its own rules, and one shared prompt guideline covers the family. The namespace object is built without a `ToolNamespace` annotation so the package still type-checks against 0.99.0. The declared tools cost about two and a half times the characters of the single `dap` tool. Exposure, namespaces, annotations, and output schemas require Pi 0.99.0 or later.
