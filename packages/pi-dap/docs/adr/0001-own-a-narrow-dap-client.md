# Own a narrow DAP client

`@ian-pascoe/pi-dap` owns a narrow Debug Adapter Protocol client with explicit Pi settings, one active Debug Session, and configured stdio or TCP adapters. It supports the core launch, source-breakpoint, execution-control, stack, variable, evaluation, status, and stop workflow while deliberately excluding adapter discovery, an adapter catalog, `launch.json`, attach, advanced protocol operations, persistence, and a directly operated debugger UI. Its non-authoritative Observer UI may present activity and results already received, but it sends no Debug Adapter request and offers no human debugger controls. The Supported `vscode-js-debug` workflow may open its one adapter-requested primary target channel against the same owned adapter process; unrelated, second, and nested `startDebugging` requests remain rejected. This trades protocol breadth for a small testable lifecycle while preserving one model-facing Debug Session and first-class Node compatibility.

> **Amended by #422.** Refusing a `startDebugging` request for a Child session left vscode-js-debug holding that child paused until a session started it, so launches hung until the execution timeout. Pi DAP may now open non-model-facing release channels against the same adapter process, one per refused Child session, used only to start the child without breakpoints. A release channel stays attached until its child terminates or the Debug Session ends, continues any stop, and refuses and releases the child's own children the same way. No events, output, state, or breakpoints from a release channel reach the model, and the `startDebugging` reply stays a failure. The model-facing Debug Session is still the one primary target channel, and Pi DAP still does not debug child targets (#421).

> **Superseded in part by ADR-0003 (#421).** With the Supported `vscode-js-debug` adapter, Pi DAP now debugs Child sessions instead of refusing and releasing them: each nested `startDebugging` request opens a target channel that gets Desired Breakpoints, and its stops are reported one at a time inside the one model-facing Debug Session. Release channels are gone. Other adapters' `startDebugging` requests are still refused, and there is still one model-facing Debug Session.
