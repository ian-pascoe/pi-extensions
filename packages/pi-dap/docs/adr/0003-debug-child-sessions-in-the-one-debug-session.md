# Debug Child sessions inside the one Debug Session

With the Supported `vscode-js-debug` adapter, Pi DAP debugs Child sessions (worker threads, child processes, and their own children) inside the one model-facing Debug Session. This supersedes the parts of ADR-0001 and its #422 amendment that refuse every nested `startDebugging` request and release the child undebugged. Refusing children meant breakpoints in them never bound, so code run by vitest's `forks` and `threads` pools, and by many servers and build tools, could not be debugged (#421).

For each `startDebugging` request on a target's channel, Pi DAP opens another target channel against the same adapter process. It initializes the channel, sends the request's `launch` or `attach` configuration, applies Desired Breakpoints, and sends `configurationDone`, so breakpoints bind before the child runs. vscode-js-debug asks for a child's own children on that child's channel, so nesting needs no special case. Other adapters' `startDebugging` requests are still refused. Any request Pi DAP cannot complete, such as a failed attach, is answered with a failure and reported once in `rejected_child_sessions`; a channel that attached and then failed is detached, so the adapter runs the child without a debugger.

Child sessions fold into the existing Debug Session as Debug targets alongside the primary target; the tools gain no target parameter:

- **Stop focus.** One stop is reported at a time. The target that stopped becomes the focus, and `dap_stack`, `dap_variables`, `dap_evaluate`, `dap_continue`, and the step tools act on it. A stop in a Child session names it in `child_session`. A target that stops while another target's stop is reported keeps its stop waiting. After the focused target is resumed or stepped, or the request to do so fails, the stop that has waited longest is reported at once.
- **Pause.** `dap_pause` pauses the primary target and every Child session, best effort for children, and reports the first stop. The rest wait their turn.
- **Thread ids.** Every vscode-js-debug target numbers its own threads, often from the same values, so Pi DAP assigns its own thread ids in that mode. Adapters without target channels keep their thread ids unchanged. A `thread_id` passed to `dap_stack` must belong to the focused target.
- **Breakpoints.** `dap_set_breakpoints` sends to the primary target and, best effort, to every Child session, including one that became ready during the call. A Breakpoint is reported verified when any target verified it, because only the child may load the code. Each target gives its own ids, so the reported id is the primary target's for that Desired Breakpoint, else the first child's, and a child's `hitBreakpointIds` are translated to the reported ids.
- **Stops nobody asked for.** `debugger;` statements and exception stops in a child are reported like the Debuggee's own, rather than continued automatically.
- **Lifetime.** A Child session's `terminated` closes only its channel; if it was the focus, focus returns to the primary target and any waiting stop is reported. A child's `exited` is ignored, so the exit code is still the Debuggee's. The Debug Session still ends when the primary target and the root channel end. `dap_stop`, failures, and shutdown detach every Child session channel before shutting down the primary target and the root channel.

Debugging children is the default because `vscode-js-debug` already attaches them by default. `launch_arguments: { autoAttachChildProcesses: false }` opts out per launch for child processes; worker threads have no such switch. Explicit target selection was rejected. It would add a parameter to most tools, change the cached tool prefix, and make the model manage targets that a test runner creates and destroys on its own. Pausing every target whenever one stops was also rejected, because a stop would then disturb parallel workers that never reached a breakpoint.

Known limits: Stack Frame ids and variables references are the adapter's, and each target numbers its own, so an id kept from an earlier stop in another target can resolve in the focused one instead of failing. A Child session whose channel cannot be opened at all is reported in `rejected_child_sessions`, but nothing starts it, so vscode-js-debug may hold it paused until the execution timeout, as before #422's release channels.
