# Implement a complete MCP Host

`@ian-pascoe/pi-mcp` implements the complete core MCP Host surface supported by the official TypeScript client SDK rather than adapting only MCP tools. It includes current and legacy protocol negotiation; stdio, Streamable HTTP, and legacy SSE transports; and core tools, resources, prompts, elicitation, roots, sampling, logging, progress, cancellation, and instructions. Current multi-round-trip input requests use the SDK's automatic fulfilment and fixed ten-round limit, while legacy peers retain server-initiated requests. Standard Extensions are outside the package contract.

Server Tools map to individual Pi tools. Resources use the fixed `list_mcp_resources`, `list_mcp_resource_templates`, and `read_mcp_resource` tools, active only while their capability is available. MCP Prompts enter through `/mcp prompt`, with protocol completion backing argument autocomplete; invocation persists the role-faithful messages and immediately begins a model turn. Subscriptions, status, reconnect, authentication, logs, and all persistent configuration operations remain human-facing `/mcp` and standalone CLI operations rather than model tools. This follows OpenCode's narrow capability-specific surfaces instead of exposing a generic protocol gateway.

Enabled servers begin connecting in the background at Pi session start without blocking startup or TUI rendering, and every connection remains owned by that session. Interactive requests fail closed without a supported UI. MCP content maps losslessly where Pi has native text or image content and otherwise remains accessible through labelled text, session files, and bounded structured details. Large results use the repository's 2,000-line or 50-KB response limit and Result Spills. This accepts a broader runtime and UX boundary in exchange for protocol-complete Pi interoperability.

Server Tool names use the stable `mcp__<server>__<tool>` namespace. Catalog additions and replacements take effect immediately. Because Pi 0.84.2 exposes activation but no public deregistration API, catalog removals deactivate their Server Tools for the rest of the session; reload fully discards dormant definitions.

Names that collide after sanitization receive deterministic hash suffixes. Server Tool annotations remain untrusted metadata that does not grant permission or alter execution. MCP Prompts are addressed as `/mcp prompt <server> <prompt>` rather than occupying global command names. Resource subscriptions are similarly explicit `/mcp subscribe` and `/mcp unsubscribe` operations; reading a resource never subscribes implicitly.

Before the first model request, the Host waits only for a bounded initial connection deadline and then freezes a deterministically ordered Instruction Snapshot for the session. Late Server Instructions wait for reload or a new session, preserving an identical system prompt across turns. Sampling uses Pi's active model and credentials without package-owned approval UI or a sampling-specific policy hook; other extensions may gate the surrounding Pi tool call. It advertises request-scoped sampling tools and returns the model's tool-use blocks for the server to execute, but does not advertise deprecated sampling context inclusion. Elicitation uses Pi's standard dialogs, requires consent before presenting a server-provided URL as accepted, and declines without supported UI.

The package owns no permission or approval policy for Server Tools, resources, MCP Prompts, or sampling. They remain ordinary Pi operations that another extension may govern. Elicitation dialogs and explicit OAuth are protocol interactions rather than permission prompts.

Server Tool schemas remain exact JSON Schema rather than being silently simplified for a model provider. The Host validates each schema structurally before registration. Pi 0.84.2 exposes no public provider-schema compatibility preflight, so a model provider may reject an otherwise valid exact schema and fail that model turn. The package does not maintain a provider matrix, rewrite the schema, inspect private Pi modules, or rewrite provider payloads to hide this limitation. Structured content remains model-visible as labelled JSON and in result details, and is validated against an advertised output schema without discarding accompanying text or images when the server violates it. Tool annotations remain untrusted diagnostic metadata and never alter permission or execution behavior.

Subscribed resource changes queue only a provenance-labelled next-turn notice until the model explicitly reads the resource. Desired subscriptions persist as Pi custom entries, while MCP Prompt expansions persist as custom messages whose versioned details a `context` hook expands role-faithfully in place. Replay uses only the active session branch; logs and connection objects remain ephemeral. List operations aggregate at most 1,000 protocol pages, keep cache-hinted results only for the session, and invalidate them on matching change notifications. Active-call progress streams through Pi tool updates; other server logs remain in a bounded human-facing tail. Resource updates and cancellation do not trigger model turns.

All transports share one bounded, host-wide retry policy configured under `mcp.retry`. Retryable initial failures and unexpected closures use capped exponential backoff; authentication, configuration, protocol-support, disable, and shutdown outcomes never retry. Exhausted servers remain failed until explicit reconnect, reload, or a new session.

The standalone `pi-mcp list` command remains offline and reports configuration provenance, enabled state, and stored authentication state without launching servers. Test operations require one server name unless `--all` explicitly selects every enabled server; `/mcp test` uses temporary connections and never disturbs live clients. `/mcp` mirrors every standalone operation and adds live status, reconnect, prompt, subscription, and log commands; bare `/mcp` shows status and concise help. Live status uses the states `disabled`, `connecting`, `connected`, `needs_auth`, `needs_client_registration`, `retrying`, and `failed`. Runtime connection failures remain isolated to their server. Pi 0.84.2 may let a provider reject an otherwise valid exact Server Tool schema and fail that model turn. Each server retains at most 256 KB of stderr and MCP logging notifications. For stdio servers, stdout remains exclusively protocol framing while bounded stderr joins that human-facing log tail; neither stderr nor logs write directly into Pi's TUI, JSON, or RPC output.
