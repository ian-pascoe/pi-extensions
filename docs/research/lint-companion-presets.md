# Lint-companion LSP presets: research

**Scope.** Primary upstream docs/package/release metadata were checked 2026-09-11. The local Pi domain is authoritative for terminology and policy: presets are package-owned fallbacks; external installations precede managed ones; acquisition is lazy/private; explicit definitions shadow all presets. The user has since accepted all three companions, project-declared/enabled activation, and requested guarded fixes rather than automatic fixes; the [design plan](../plans/language-tool-preset-expansion.md) is authoritative. The user also accepted private opt-in type-aware helpers; exact mappings and integration proofs remain outstanding. [ADR-0006](../adr/0006-separate-installer-and-preset-platform-support.md) now distinguishes six-platform installer support from potentially narrower per-preset support.

## Executive findings

- **Biome** and **Oxlint** have maintained native LSP entry points and published native artifacts for Linux/macOS/Windows x64+ARM64. They are plausible managed presets, but release/package metadata is not proof of startup on all six targets; each needs native acquisition/launch probes for its declared supported platforms.
- **ESLint does have an official published VSIX.** The maintained server is the server component of Microsoft's `dbaeumer.vscode-eslint` extension, not a standalone official LSP npm package. The official Marketplace/Open VSX release is concrete version **3.0.34**; GitHub's zero release assets do not mean there is no usable official artifact.
- Every candidate must remain a separate matching server if enabled. Pi's current explicit-definition shadowing and multi-server behavior must not infer that ESLint, Biome, or Oxlint complements TypeScript or one another ([`packages/pi-lsp/CONTEXT.md`](../../packages/pi-lsp/CONTEXT.md); [`docs/plans/managed-language-tools.md`](../plans/managed-language-tools.md)).

## ESLint identity, released artifact, dependencies, and packaging

**Identity and release.** Microsoft's maintained project is `microsoft/vscode-eslint`, published as VS Code extension `dbaeumer.vscode-eslint`. The official Marketplace identifies Microsoft as publisher and reports release 3.0.34 ([Marketplace](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint)); GitHub's latest release API is `release/3.0.34` (published 2026-07-16, no GitHub release assets) ([release metadata](https://api.github.com/repos/microsoft/vscode-eslint/releases/latest)). Open VSX independently exposes a **downloadable, universal** `dbaeumer.vscode-eslint-3.0.34.vsix`, MIT license, exact version, `targetPlatform: universal`, `verified: true`, and separate VSIX signature/SHA-256/public-key endpoints ([Open VSX metadata](https://open-vsx.org/api/dbaeumer/vscode-eslint)). This is evidence of a released distributable and integrity metadata, not proof that Pi may blindly trust/rehost it: acquisition should verify the advertised digest/signature and preserve the MIT/third-party notices.

**Entrypoint layout.** The official source's webpack config sets entry `./src/eslintServer.ts`, output filename `eslintServer.js`, and output directory `server/out` ([webpack config](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/server/webpack.config.js)). The official `.vscodeignore` excludes `server/**` but explicitly re-includes `server/out/eslintServer.js`, proving the server entrypoint is intentionally packaged in the VSIX ([`.vscodeignore`](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/.vscodeignore)). The VSIX manifest's extension `main` remains `./client/out/extension`; Pi would launch the packaged server entrypoint directly under a private Node runtime, not load the VS Code client. The server source creates an LSP connection and calls `connection.listen()` for stdio ([server source](https://github.com/microsoft/vscode-eslint/blob/main/server/src/eslintServer.ts)).

**Not the alternatives.** There is no official standalone ESLint-server npm package: registry `vscode-eslint@0.0.6` is a different third-party fork (`shubham151/vscode-eslint`) ([registry metadata](https://registry.npmjs.org/vscode-eslint/latest)). `vscode-langservers-extracted@4.10.0` is a community extraction last published in May 2024; its README says the ESLint server is “Not yet” ready even though a bin name appears in metadata ([README](https://github.com/hrsh7th/vscode-langservers-extracted), [npm metadata](https://registry.npmjs.org/vscode-langservers-extracted/latest)). It should not be the maintained preset identity.

**OpenCode comparison (reference only).** At pinned commit `43e89ea1673937c325edb922eaa1a768aa0e5bf4`, OpenCode resolves a project ESLint module, downloads Microsoft's `main.zip`, runs `npm install` and `npm run compile`, then launches `node .../server/out/eslintServer.js` ([source at pinned commit](https://github.com/anomalyco/opencode/blob/43e89ea1673937c325edb922eaa1a768aa0e5bf4/packages/opencode/src/lsp/server.ts#L174-L222)). This is a source-build recipe, not the preferred concrete release path and not a reusable catalog.

**Project requirements and protocol fit.** The official server loads the ESLint library from the opened workspace (local recommended; global fallback), plus project config, plugins, parsers, and shareable configs. ESLint documents that plugins/config packages are project npm dependencies referenced by `eslint.config.*` ([README](https://github.com/microsoft/vscode-eslint/blob/main/README.md), [configuration](https://eslint.org/docs/latest/use/configure/configuration-files), [plugins](https://eslint.org/docs/latest/use/configure/plugins), [shareable configs](https://eslint.org/docs/latest/extend/shareable-configs)). Pi must not install these into projects; a managed VSIX/Node runtime alone cannot make a project lintable.

Flat-config and ignore behavior differs materially from legacy: flat config is default since ESLint 9; `.eslintignore` and `--ignore-path` are not supported in flat config, while legacy `.eslintrc` uses `.eslintignore` ([migration/ignore docs](https://eslint.org/docs/latest/use/configure/migration-guide), [ignore docs](https://eslint.org/docs/latest/use/configure/ignore)). A root-marker heuristic must not claim “configured” merely from a package manifest; nested configs/working directories and missing project libraries remain meaningful outcomes.

The current official server advertises incremental sync, document diagnostic pull (`diagnosticProvider`, `workspaceDiagnostics: false`), and code actions ([raw server](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/server/src/eslintServer.ts)); its changelog records conversion from push to pull in 3.0.5 ([changelog](https://github.com/microsoft/vscode-eslint/blob/main/CHANGELOG.md)). Code actions include direct fixes, disable-rule edits, documentation commands, and `source.fixAll.eslint`. These fit Pi's guarded Workspace Edit Preview, but command-bearing actions and server `workspace/applyEdit` must remain unapplied previews ([Pi client contract](../../packages/pi-lsp/src/lsp-server-client.ts), [workspace-edit boundary](../../packages/pi-lsp/README.md#workspace-edit-preview-and-apply)).

**Recommendation.** Reserve an ESLint preset identity in the all-at-once curated expansion and prefer the exact official 3.0.34 VSIX (Marketplace or integrity-verified Open VSX artifact) over `main.zip`, the stale extractor, or an unrelated npm fork. The private acquisition mapping and six-cell launch/protocol evidence remain unproven. Trace the existing mise backends and archive handling before adding any extractor; a VSIX artifact does not by itself establish either complete support or the need for a new installer backend. Keep project ESLint/plugin/config dependencies external and do not install them.

## Biome

**Identity/artifacts.** The maintained tool is `@biomejs/biome`; its CLI is `biome`/`biome.exe`. The exact documented LSP command is **`biome lsp-proxy`**—the official CLI reference lists that subcommand and says it forwards LSP over standard input/output ([CLI](https://biomejs.dev/reference/cli#biome-lsp-proxy)); the official third-party-extension example uses `args = ["lsp-proxy"]` ([Helix integration](https://biomejs.dev/editors/third-party-extensions)). `--stdio` is not shown as a supported proxy argument in the current CLI reference, so `biome lsp-proxy --stdio` must not be assumed; only use it if a target version's own help/source proves acceptance.

The npm latest metadata observed was 2.5.13 with optional native packages for `@biomejs/cli-linux-arm64`, `linux-x64`, `darwin-arm64`, `darwin-x64`, `win32-arm64`, and `win32-x64` (plus Linux musl variants) ([npm metadata](https://registry.npmjs.org/@biomejs/biome/latest)). The matching release API lists named native assets `biome-{darwin,linux}-arm64/x64` and `biome-win32-arm64/x64`, with SHA-256 digests ([release metadata](https://api.github.com/repos/biomejs/biome/releases/latest)). Biome's CLI docs say the native executable does not require Node ([CLI](https://biomejs.dev/reference/cli)). This is a strong six-target artifact signal, not a launch guarantee.

**Lifecycle hazard.** `lsp-proxy` ensures a daemon and forwards stdio; the proxy is not the whole process tree. Biome explicitly says the integrator is responsible for `biome stop` to avoid ghost processes ([LSP lifecycle docs](https://biomejs.dev/editors/introduction), [CLI stop](https://biomejs.dev/reference/cli#biome-stop)). Pi's normal Server Instance shutdown can terminate the proxy, but does not inherently reap the daemon. Calling `biome stop` on every instance can kill a daemon shared by other Pi sessions/roots. Daemon scoping/ownership and safe concurrent cleanup need a targeted probe/design; ordinary child-process cleanup is insufficient.

**Configuration and overlap.** Biome configuration has independent `formatter.enabled` and `linter.enabled` (also language-specific switches), plus `files.includes`, tool includes, VCS ignore integration, and nested configuration ([configuration guide](https://biomejs.dev/guides/configure-biome), [configuration reference](https://biomejs.dev/reference/configuration)). LSP settings include `require_configuration`, `configuration_path`, and `inline_config`; inline config overrides on-disk config ([LSP settings](https://biomejs.dev/editors/introduction#extension-settings)). A lint companion must not inject an inline “formatter off” object without deciding whether that overrides project policy. The server advertises formatting and formatting code actions, so overlap with Pi Formatter is a routing/policy question, not solved by naming it a linter.

Biome supports `.gitignore`/VCS and Biome include/ignore semantics; ignored/indexed files and nested configs need tests. Its documented LSP methods list `textDocument/publishDiagnostics` (push), code actions/resolve, and formatting, but not `textDocument/diagnostic` or workspace pull ([supported methods](https://biomejs.dev/editors/introduction#supported-methods)). Pi should expect push diagnostics and cached workspace fallback, not fresh pull diagnostics. Code actions and formatting return edits that fit Pi's preview/guarded-apply path, but exact fix kinds and stale-version behavior require integration tests.

**Recommendation.** Biome is a good candidate for a managed six-target preset if daemon cleanup and lint/format overlap are resolved. Keep project config authoritative; do not use `biome migrate eslint` or any command that writes project files as part of acquisition/activation ([CLI migration](https://biomejs.dev/reference/cli#biome-migrate)).

## Oxlint

**Identity/artifacts.** Oxlint's maintained native LSP is the `oxlint --lsp` mode ([CLI](https://oxc.rs/docs/guide/usage/linter/cli.html), [editor setup](https://oxc.rs/docs/guide/usage/linter/editors.html)); `oxc_language_server` is an older/alternate binary seen in OpenCode, not the identity to require. The npm latest metadata observed was `oxlint@1.82.0`, whose `bin/oxlint` wrapper has optional `@oxlint/binding-*` packages for Linux/macOS/Windows x64+ARM64 (and additional platforms) ([npm metadata](https://registry.npmjs.org/oxlint/latest)). Native release metadata likewise lists `oxlint-aarch64-apple-darwin`, `oxlint-aarch64-pc-windows-msvc`, `oxlint-aarch64-unknown-linux-gnu`, and x64 counterparts ([release `apps_v1.82.0`](https://github.com/oxc-project/oxc/releases/tag/apps_v1.82.0)). Verify the exact native selector/executable on each six target; package availability alone is not protocol evidence.

**Runtime/project requirements.** `.oxlintrc.json`/`.jsonc` work with standalone native binaries. `oxlint.config.ts/.mts` is experimental and requires the Node-based package plus a Node version capable of executing TS; docs state Node v22.18+ or v24+ ([configuration](https://oxc.rs/docs/guide/usage/linter/config.html)). Type-aware linting is a separate tsgolint component and requires `oxlint-tsgolint` plus resolved project dependencies/TypeScript programs; it can be enabled by root config `options.typeAware` or LSP `typeAware` ([type-aware docs](https://oxc.rs/docs/guide/usage/linter/type-aware.html), [npm metadata](https://registry.npmjs.org/oxlint-tsgolint/latest)). Do not install that dependency into projects. Do not promise type-aware diagnostics unless private acquisition/injection and project resolution are proven.

**Config/ignore/nested behavior.** Oxlint discovers `.oxlintrc.json`, `.oxlintrc.jsonc`, `oxlint.config.ts`, and `.mts`; nearest nested config is used, and explicitly passing `configPath` or `--disable-nested-config` disables nested lookup ([nested config](https://oxc.rs/docs/guide/usage/linter/nested-config.html)). It recommends config `ignorePatterns`, supports `.eslintignore` compatibility, and filters directory discovery through `.gitignore` ([ignore docs](https://oxc.rs/docs/guide/usage/linter/ignore-files)). This creates overlap/precedence questions with ESLint and Biome in the same JS/TS files; Pi should preserve independent server diagnostics rather than deduplicate by rule name.

**LSP diagnostics/fixes.** Native Oxlint supports pull diagnostics when the client supports diagnostic pull plus refresh; otherwise its `run` option controls push timing (`onSave`/`onType`). LSP options include `configPath`, `disableNestedConfig`, `tsConfigPath`, `typeAware`, `fixKind`, `rulesCustomization`, and `unusedDisableDirectives` ([LSP options](https://oxc.rs/docs/guide/usage/linter/lsp-config-reference.html)). The native server documents quickfix and `source.fixAll.oxc`, including `oxc.fixAll`; fix generation can be restricted by `fixKind` ([server README](https://github.com/oxc-project/oxc/blob/main/crates/oxc_language_server/README.md)). Pi's capability negotiation should select pull vs push/cache correctly, and all quickfix/source-fix workspace edits must remain guarded previews.

**Recommendation.** Oxlint is the strongest native candidate for a lint-only preset, subject to six-target acquisition/startup probes and an explicit policy for `.oxlintrc`/nested configs, `.eslintignore` compatibility, type-aware project libraries, and `fixKind`. Do not infer “native on all six” from OpenCode's lockfile or a generic npm install; its pinned implementation probes `--help` for `--lsp` and falls back to `oxc_language_server` ([pinned source](https://github.com/anomalyco/opencode/blob/43e89ea1673937c325edb922eaa1a768aa0e5bf4/packages/opencode/src/lsp/server.ts#L225-L295)).

## Follow-up: privately supplying the type-aware helper

Released `oxlint@1.82.0` declares optional peer `oxlint-tsgolint >=7.0.2001`, not
an equal Oxlint/helper version. `oxlint-tsgolint@7.0.2001` publishes exactly six
native packages for Linux/macOS/Windows x64+ARM64; its wrapper resolves the
platform's `tsgolint` executable. This is artifact evidence, not a Pi launch proof.

Oxlint's tagged helper lookup first accepts `OXLINT_TSGOLINT_PATH`, then searches
ancestor project `node_modules/.bin` directories, then PATH. Pi can therefore pass
a private absolute helper executable without editing project dependencies. Use an
executable path, particularly on Windows: the environment-directory branch appends
`tsgolint` without `.exe`. The LSP `typeAware` option enables the feature but does
not itself select the helper path. Any managed fallback must preserve compatible
External Installation precedence rather than blindly setting the environment first.

The source starts `tsgolint headless`; it does not perform an exact-version
handshake. The helper's version tracks TypeScript Go, and the published peer range
is the compatibility signal, not proof that arbitrary newer pairs work. Private
helper acquisition does not supply a project's dependencies or built `.d.ts`
outputs; those remain project inputs. The TypeScript 7 requirement describes the
helper's compiler baseline, not a requirement to install npm TypeScript into every
project. Automatic helper provisioning, opt-in behavior, and six-cell type-aware
protocol evidence still need agreement and verification.

## Cross-cutting decision constraints

1. **Explicit precedence:** ESLint/Biome/Oxlint definitions must be treated like any other explicit server. An explicit definition (including null/quarantined same-ID replacement) suppresses presets; disabled or failed explicit configuration must not resurrect a preset. This matches current `withLspPresets` and settings contexts ([`lsp-presets.ts`](../../packages/pi-lsp/src/lsp-presets.ts#L63-L75), [`pi-lsp/CONTEXT.md`](../../packages/pi-lsp/CONTEXT.md)).
2. **Activation:** Candidate root markers should identify actual tool configuration where possible, but “no config” differs by tool: Biome intentionally supports zero-config defaults; Oxlint has defaults but project config controls rules; ESLint needs a project ESLint library/config. Exact activation gates remain unapproved.
3. **Diagnostics:** ESLint is document-pull; Oxlint prefers pull but supports push fallback; Biome documents push only. Pi already models fresh pull and cached push outcomes ([`lsp-server-client.ts`](../../packages/pi-lsp/src/lsp-server-client.ts#L123-L139)). Do not call server startup “useful diagnostics” until each mode is probed and missing/ignored files are characterized.
4. **Edits:** All three can expose fixes; ESLint also emits command-bearing actions, Biome has codeAction/resolve, and Oxlint has quickfix/source-fix-all. Keep command actions visible but unapplied where no safe Workspace Edit exists, and run all edits through Pi's source-version/hash guarded preview.
5. **Private acquisition:** Biome/Oxlint npm optional-native packages fit the existing private `ToolInstaller` selector shape in principle. ESLint's official VSIX is now a concrete release path, but VSIX acquisition/extraction/integrity verification is not an existing ToolInstaller selector and needs explicit mapping. No project dependency installation is acceptable for any candidate.
6. **Platform gate:** The installer retains its six-cell native gate; each preset needs evidence for its declared supported subset. Record exact versions/artifacts and launch probes. A declared unsupported platform is not itself a release blocker, but missing proof for claimed support cannot be disguised as success.
